# MetroFuse plugin SDK

Reusable plugin UI lives in this module. Plugins own their account screens, provider URLs, navigation rules, labels and session verification. The SDK supplies `WebViewLoginScreen`, Android WebView, desktop WebView and the generic Windows WebView2 helper. The application hosts `NativeLoginUi` contributions through `LoginUiContext` and handles owner-scoped credential persistence.

Desktop login dialogs retain the host's Material theme and surface colors. On Windows, the SDK writes the browser request to a temporary UTF-8 JSON file and passes its path to the helper; JSON is never placed in Windows command-line arguments. Invalid requests return a failure status to the retry UI. `:plugin-sdk:desktopTest` checks this transport against the published helper without opening a browser or signing in.

Windows browser diagnostics reach the application's log through the helper's error stream. They report page origins, navigation and network failure codes, and whether the requested service cookie is present. Passwords, cookie values, request bodies, URL paths, queries, fragments and exception messages are excluded.

Requests declaring required session cookies check the configured service cookie URL while any allowed sign-in page is open. A phone approval can finish as soon as those cookies arrive, even when an identity-provider redirect is still pending. An explicit `completionPath` continues to require the configured cookie origin and exact path. The calling plugin verifies the captured account before accepting or saving it.

Native plugins compile against both `plugin-api` and `plugin-sdk` JARs with the host's Kotlin and Compose versions. Keep both dependencies compile-only in production: their classes are supplied by the host and must never be bundled into a plugin JAR or APK. JavaScript plugins return `{request, labels}` from `host.login`'s `ui` callback to contribute the SDK's browser screen.

Export the JARs with `:plugin-api:desktopJar :plugin-sdk:desktopJar`. Windows packaging needs .NET SDK 10 and restores Microsoft.Web.WebView2 1.0.4314.35. Use `-PdotnetExecutable=<path>` when .NET is outside PATH. The SDK JAR embeds the helper as a resource, so installed native plugins use the same SDK browser as MFP plugins.

The Windows browser uses a private profile beneath its SDK-owned temporary directory, cleaned after exit or cancellation. Android uses the process WebView cookie store and blocks screenshots. Linux checks its WebKitGTK libraries before composing the browser. Session candidates are delivered through the plugin's activation-scoped callback; plugins must verify their service account before accepting them.

See the public [browser sign-in guide](https://github.com/956tris/MetroFuse-Plugin-Docs/blob/main/docs/browser-login.md) and separate [YouTube Music reference plugin](https://github.com/956tris/MetroFuse-YouTube-Music).

See [UI plugins](ui-plugins.md) for the application shell, player UI, native and JavaScript APIs, and recovery.

Catalog providers can also implement `RecommendationProvider`. The host sends a `RecommendationRequest` containing the seed's provider identity and, for subsequent pages, that provider's continuation. Return `RecommendationResult(tracks, continuation)`; the host assigns track ownership and keeps continuation tokens tied to the provider and activation. JavaScript uses `host.catalog(id, { recommendations: async request => ({tracks, continuation}) })`. The existing autoplay preference controls queue generation, and the host falls back to playable local, downloaded and cached audio when the selected source is offline or cannot supply recommendations.

Native Home providers can implement `PagedHomePlugin` and return `HomePage(shelves, continuation)` from `getHomePage(request, continuation)`. JavaScript Home callbacks may return the same object and receive `request.continuation`. The host loads additional pages when the user scrolls toward the end, preserves current shelves on a page failure, and rejects stale pages after account changes or plugin unload. Older `HomePlugin` implementations and JavaScript callbacks returning shelf arrays remain supported.

Catalog providers may implement `LibraryProvider` to expose their account library. Return `LibraryPage(items, continuation, complete)` from `library(LibraryRequest)`; items use `HomeItem` for songs, albums, artists and playlists. JavaScript registers `host.catalog(id, {library: async request => ({items, continuation, complete})})`. Requests contain the host's content language and country. The host assigns object ownership, pins continuations to the provider and activation, and displays pages as they arrive. Set `complete = false` for partial results. Sign-in, sign-out and source changes clear the previous account's cache and reject late results. Desktop, Android and UI plugins share the selected source's Library model; local and downloaded music remains available offline. Providers without this optional interface retain their locally saved content.

Providers exposing liked songs opt in with `supportsLikedSongs` and handle `LibraryRequest.likedSongsOnly` as a separate paginated song list. Native providers opt in to song voting with `supportsSongVotes` and implement `setSongVote(SongVoteRequest)` using the provider's track ID and `TrackVote`. JavaScript catalogs declare `supportsLikedSongs: true` and expose `setSongVote(request)`. Return true only after the service accepts the vote. A track's `extras.likeStatus` may carry `LIKE`, `DISLIKE` or `INDIFFERENT`; the host applies it without replacing a newer pending user choice. The host uses the selected plugin account for these operations.
